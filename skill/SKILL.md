# Deep research

Процесс поверх сервера `research-state`. Сервер держит состояние и проверяет цитаты;
думает клиент. Поиск и выкачка — сервер `search` (free-search-mcp).

## 1. Сначала библиотека, всегда

`research_start(topic)` возвращает `job_id` и похожие прошлые брифы. **Если бриф
отвечает на вопрос — прочитать файл и остановиться.** Повторный вопрос должен стоить
около нуля. Это верно и для быстрого режима.

## 2. План подвопросов

`research_plan(job_id, subquestions)` — 3–5 для обычного режима, 5–8 для глубокого.
Подвопросы в одном заходе должны быть независимы: параллельные ветки, строящие на
допущениях друг друга, дают противоречивые выводы.

Уровень можно поднять на ходу — `research_plan` дописывает, не начиная заново.

| | quick | normal | deep |
|---|---|---|---|
| План | нет | 3–5 | 5–8 + второй проход по незакрытым |
| Страниц | 0, по сниппетам | до 5 | до 15 |
| Ответ | 3–5 строк | ≤1500 токенов | ≤3000 + файл, раздел «пробелы» |

## 3. Сужение области поиска

Качество определяется подготовкой контекста, а не поиском. `search` принимает
`include_domains`, `exclude_domains`, `freshness`, `category`.

| Тип темы | Фильтр |
|---|---|
| Вакансии, рынок труда | `include_domains=["hh.ru"]` |
| Дока продукта/SDK | домен вендора либо `category="github"` |
| Нормативы РФ | `pravo.gov.ru`, `consultant.ru`, `garant.ru` |
| Научные статьи | `category="paper"` |
| Свежие новости | `category="news"` + обязательно `freshness="day"` |
| Остальное | без фильтра |

**Год указывать в каждом запросе, где важна свежесть.**

## 4. Выкачка — в субагенте, чтение — фрагментами

Поиск и выкачку делегировать субагенту `research`: он возвращает список
`{url, title}` и по строке, чем страница полезна. **Текст страниц наверх не поднимать.**

Один простой вопрос субагента не получает — делать напрямую.

Дальше по каждому url: `fragments_for(url, query)`, где `query` — подвопрос, а не тема
целиком. `fetch` целой страницы в главный контекст — нарушение всей затеи.

## 5. Закрывать подвопросы по мере ответов

`research_mark(job_id, subq_id, answer)` — одно-два предложения, не сырьё.
Перед финалом `research_gaps(job_id)`.

## 6. Сначала синтез прозой, потом упаковка

Написать выводы свободным текстом. **Затем** отдельным шагом собрать
`research_finish(job_id, summary, claims, gaps)`. Формулировать выводы прямо в момент
заполнения полей — измеримо хуже по качеству рассуждения.

Каждый факт: `{text, kind: "fact", fragment_id, quote}`, где `quote` скопирована
дословно из фрагмента — сервер проверяет вхождение, приблизительная цитата отвергается.
Два правила измерены, а не назначены (`eval/RESULTS.md`):

- **Не короче пяти слов.** Более короткая цитата слишком часто встречается и в других
  фрагментах, то есть не подтверждает ничего; ответ — `quote_too_short`.
- **Середину можно опустить** через `…` или `...`: «начало … конец». Куски должны идти
  дословно и по порядку внутри одного фрагмента; слова считаются суммарно по кускам.
Что не подтверждено источником — либо `kind: "assumption"` (напечатается как
предположение), либо в `gaps`.

Незакрытые подвопросы без записи в `gaps` финал не пропустит.

## Чего не делать

- Не звать `fetch` в главном контексте ради «прочитать статью целиком».
- Не ставить `fragment_id` наугад, чтобы прошла проверка: цитата всё равно сверяется.
- Не начинать новый job, когда нужно углубить текущий.
- Не пропускать шаг 1 — библиотека проверяется даже в quick.
